# Grind — autonomous backlog loop

## Purpose

Turn "review the backlog and get after it" into a disciplined, repeatable loop: groom → orient → plan lanes → understand → implement/critique/test/critique per lane → reconcile the lanes → track & groom → hand off → clean up. High agency, bounded by principle. Act when you have enough to act; ask only on genuine judgment calls.

**Lanes are the default shape of a session, not an optimization.** A grind session fills concurrent lanes of worktree-isolated agents and reconciles them through one integration branch, whose combined diff gets the critique. One item at a time is the *degenerate* case — correct only when the groomed queue holds a single item, or when everything else in it lands in the same files as the spine item (§1). Running serially by habit spends the session's wall-clock on the narrowest thing it could have been doing.

**Critique early and often, and act on it.** The loop below critiques three times — at the design, at the first working cut, and at the finished diff — because a critique's leverage collapses as the work hardens around it. The last one can fix a bug; only the first two can tell you the design is bigger than the problem. And a finding is only addressed when it is fixed, filed, or declined out loud — by value, never by effort (§3.6).

Optional `$ARGUMENTS` narrow the scope (e.g. `/grind phase-0 fidelity bugs`, `/grind MAR-120`). With none, groom, then work the active queue.

***

## 0. Groom the queue first (before picking anything)

**A starved queue isn't the only way this fails — nor the worse way.** A thin `Todo` reduces "pick by principle" to picking whatever's there; a *full* one fails more quietly, letting a ready, cheap item sit beside the existential one and win on readiness alone. Grooming owes the pick depth **and** an honest top — depth is the easy half.

- **Read the board guide first** (`MAR-141` — 📌 START HERE, current working order). Its stated ordering outranks your inference from labels — but **it is an artifact, not an oracle: verify it, and fix it when it has drifted.** It goes stale the moment a session ships anything, and it is written in the confident voice of a plan either way. (2026-07-15: it listed a five-item queue of which four had already shipped.) Leaving it wrong silently mis-sequences the *next* session too, so updating it is part of grooming, not a nicety. The same skepticism is owed to the tickets it points at — §2.
- **Pull wider than `Todo`**: `Todo` + `In Progress` + `Backlog`. The queue you prioritize over is the *groomed* union, not the default view. **Pull the Backlog inside a subagent** and have it return a compact table (id, title, priority, labels, updated) — a real backlog exceeds the tool-output limit and will blow up in your face mid-groom if you fetch it inline (2026-07-15: 54 issues, 74k chars, hard error). `Todo`/`In Progress` are small enough to fetch directly, in parallel.
- **Reconcile against reality — this is what makes the queue trustworthy:**
  - **Close silently-shipped work.** Cross-reference open tickets against `git log --oneline` (read diffs of recent omnibus `feat:`/`fix:` commits, not just subjects) and `CHANGELOG.md`. Verify against the working tree, never the CHANGELOG alone. Move to `Done` with the SHA.
  - **Re-scope tickets the code has outgrown** — a premise that no longer holds, or a partial fix already landed. Rewrite the title/description to what's actually left.
  - **Un-stick `In Progress`** items that aren't being worked: finished → `Done`; abandoned → back to `Todo`/`Backlog`.
- **Spine quota — the binding rule. Readiness is not a filter on the pick.** The pick is the **first High-or-Urgent item down the spine** (`phase-0-fidelity` first, then `phase-1-performance`, `phase-2-syntax`, `phase-3-interaction`, `phase-4-differentiators`; within a phase, by `priority` — `CLAUDE.md` → Issue tracking) — and **if it isn't ready, making it ready IS the work**: scope it, build the repro, bound the blast radius. If bounding it is all a session buys, that is the session's deliverable — write it into the ticket and say so. Below High the spine stops compelling (fidelity's long tail always has open Mediums; letting those compel would freeze every other phase forever); with no High anywhere, take the spine's top by `priority`.
  - Readiness is **anti-correlated** with the spine, which is why it can't be the gate: a clear repro and a known blast radius are what existential work *lacks* — not knowing MAR-120's blast radius is *why* it's phase-0, not a reason to pass over it. (2026-07-15 15:17: MAR-107 (phase-3, Low) and MAR-29 (phase-4, Low) were promoted in the same minute and both shipped by 15:59 — while MAR-120 (phase-0, **High**, #Bug, open since 07-13) sat in `Todo` untouched all day. Note the board had *already* encoded the answer in `priority`; the readiness gate overrode it. A filter that outranks both spine and priority isn't a tiebreak — it's the whole sort.)
- **The spine item is the session's opener, not its leftover.** Cheap wins aren't banned — they're what you do *after* it has had your first and best hours (MAR-107 and MAR-29 took 42 minutes between them; the day had room for both *and* MAR-120). A session ending with the spine item untouched has answered "was it of value?" with "it was easy."
- **Only *blocked* releases the quota — never *hard*.** Blocked means you can't proceed without something outside the session: an upstream decision, a fork, a user judgment call. Name the blocker in the ticket and take the next item. Vague, large, or intimidating is not blocked — that's the work, and §4's *scope honestly* is how you land part of it.
- **Promote depth behind it** — a few more items so a genuinely-blocked top has a successor. Depth is for continuity, never for choosing.
- **Disposition discovered work as you groom** rather than holding it in your head — but by the §3.6 value buckets: filing (`/devlog`) is the narrow middle bucket, not the default.
- **Burn down the deferred tail — every session, before picking.** Disposition at least 5 Backlog tickets, oldest deferred-finding tickets first (follow-ups, residuals, cleanups, polish): absorb into this session's work if they touch the same area, merge duplicates into the ticket that owns the theme, or close with a stated reason — "below the value bar" is a valid reason and closing such a ticket is grooming succeeding, not work being lost. The target shape is a backlog dominated by *features and real bugs*; one dominated by deferred critique residue is a grooming failure even when every individual ticket is defensible. **The quota is scoped to residue, not to a number**: once the tail is drained and what remains is features and real bugs, it is satisfied vacuously — never close maintainer-authored feature ideas to hit a count. The spine compels *existing* High work — never manufacture new phase-0 tickets out of hardening findings so the spine has something to point at (2026-07-17: the only phase-0 items left open were session-filed hardening residuals, not user-reachable bugs).
- **Work the do-inline ledger opportunistically.** MAR-141 carries a ledger of one-line small items (converted from canceled below-bar tickets); when the session's work touches a ledger item's area, absorb it into the same PR and check it off in the guide. Prune during groom: a line that sessions have *worked past* — its area was touched and the line still wasn't worth absorbing — has failed the value test in context; delete it, don't promote it back to a ticket. The ledger is a holding strip, not a second backlog.
- **Push the reconciliation reads into subagents** — the git-log/CHANGELOG cross-reference is exactly the broad, noisy read §2 says to delegate. Relay conclusions.
- **If grooming genuinely finds nothing open**, say so and ask — don't manufacture work to have something to do. ("Nothing *ready*" is not that case; see the quota.) `$ARGUMENTS` naming a specific ticket (e.g. `/grind MAR-120`) narrows grooming to that item's neighborhood; it doesn't skip the reconcile.

## 1. Orient, prioritize & plan the lanes (once)

- Prioritize over the **groomed** queue from §0 — never the raw `Todo` view.
- **The spine quota names the pick; convenience is not a tiebreak.** "Well-scoped, with a clear repro" describes the *runner-up* on almost every board, because the least-scoped work is usually the most existential — reaching for it is the pathology, not the principle. Honor `$ARGUMENTS` if given.
- State the pick and *why* in one line, then go. Don't narrate options you won't pursue. **If you're about to pass over a higher-spine item, that's not a preference — it's a claim that it's blocked, and it belongs in the reply and the ticket.**
- **The spine item is lane 1, and it is yours.** Fill the remaining lanes *behind* it, in groomed-queue order. Lanes never reorder the spine — they buy the session more throughput at the tail, and a session that fills three lanes with cheap work while the spine item waits has failed §0's quota in a new and more expensive way.
- **Plan lanes by file ownership, measured — not by how independent the tickets sound.** Two tickets are lane-separable when their expected diffs don't intersect. Estimate from the code (grep the symbols each ticket names, read the call sites), then treat the estimate as a hypothesis: this repo's fidelity work concentrates in a few hot files (`webview/editor.ts`, `webview/serialization.ts`, `webview/utils/minimalDiff.ts`, the fold plugins), so tickets that *sound* unrelated routinely land in the same one. Tickets that share a hot file go in the **same lane, in sequence** — the second one starts from the first one's merge. That is the answer to a collision risk; dropping to a single lane is not.
  - **Three lanes is the default ceiling**, and the cap on total tickets dispatched is the session's, not the lane's. Prefer two well-separated lanes to three with an ambiguous seam.
  - **Nothing outside a lane's ticket is the lane's to touch — `CHANGELOG.md` above all.** Lane agents write code, tests, and their own ticket comments; the orchestrator writes the CHANGELOG once, at reconciliation (§6). This is the file the handoff rules make *universal*, which is exactly why it is the empirically-observed conflict: in the one prior multi-stream run here, the predicted conflict (a shared `it.fails` map) never materialized and `CHANGELOG.md` stalled both PRs, because every stream had been told to update it. Take it out of the lanes rather than merging it three ways.
- Set up a task list (`TaskCreate`) covering every lane's tickets; keep it current as lanes complete and refill.

### Dispatching and refilling lanes

- **Brief each lane agent to run §3's work loop inside its own worktree** — reproduce, implement, critique the first cut, test, critique the diff, disposition every finding (§3.6), commit on its worktree branch. It does *not* open a PR, does not touch `main`, does not write the CHANGELOG. It ends with a handoff: what it did, what it deviated from, what it's unsure of, what it discovered, and the files it actually touched (`git diff --name-only`).
- **Give every lane agent standing to contradict its brief** (§2) — a lane brief is a longer, more confident-sounding brief than usual, which makes it a better vector for your errors.
- **Launch worktree-isolated agents one per message** (see §2's Lanes bullet for why, and for the isolation check you owe each result before believing it). Run them in the background; handle each completion as it lands rather than waiting for the wave.
- **Refill a lane the moment it drains** — the next ticket in that lane, briefed *after* its predecessor's branch has merged into the integration branch so it starts from the reconciled tree. If a lane's queue is empty, it may take an eligible ticket from another lane whose files it doesn't touch. **One refill per message too** — refills fire on completion notifications, so two lanes draining at once relaunch simultaneously and hit the same startup race a first wave would.
- **Feed each completed lane's handoff forward into the briefs you haven't sent yet** — its concerns, its deviations, and any file it touched that you didn't predict. A handoff that invalidates a queued ticket's premise re-plans that lane *now*; a queued ticket whose files a merged lane just moved gets rebriefed, not dispatched blind. This is cheap reasoning at completion time, not a fresh planning pass.
- **A lane's report is a description, not a result** (§2). Reproduce anything you're about to relay, file, or write into the CHANGELOG. The reconciliation critique in §6 is where lane claims meet a diff you read yourself.

## 2. Understand before acting

- Read the ground truth in order: the failing test / repro → the implementation it exercises → the surrounding architecture and conventions (`CLAUDE.md`, `docs/DESIGN_PRINCIPLES.md`).
- **A ticket's prescribed approach is evidence, not instruction** — the same rule §0 applies to the board guide. Its description records what someone believed when they filed it; you have the code in front of you and they didn't. Take its *problem* as the brief and its *plan* as a hypothesis. **A ticket that flags its own approach as unverifiable is naming the experiment to run first, not the thing to build.** (2026-07-15, MAR-144: the description prescribed a contributed keybinding in five numbered steps; its own "Verification note" warned the failing path was host-specific and couldn't be reproduced headlessly. The prescription was built in full — then reality rejected it: on macOS the native Option+Arrow caret-nav fires *before* an async contributed command can, so the move faithfully preserved a corrupted caret. The same PR reverted to a hardcoded chord, `c535203`.) Fidelity to a plan reality has already contradicted is not diligence.
- **The ticket's *premise* is a claim too — and premises fail as often as plans.** The bullet above quarantines the *approach*; that is not enough, because a wrong **cause** produces work that looks correct, passes its own tests, and ships. Before implementing, name the **one observation that would falsify the ticket's stated cause**, and make it. (2026-07-25, three in a single batch, all from one careful audit: MAR-214 asserted round-trip protection was the only thing preserving a lone `<br />` table cell — the normalizer already keyed that cell equal to empty, so no protection region ever formed; MAR-219 asserted `plugin-prism`'s `init` and `apply` hold two different refractor instances — `bare === core` is `true`; MAR-215 reported the fold plugin as "91%" — of the plugin-apply *slice*, not of dispatch, where it was 18%, and the cheap wins that framing implied measured ~2%, below the harness's noise gate.) An audit can be thorough about **symptoms** and unreliable about **causes**; those are separate reliabilities, and only the symptom half survives being quoted.
- **Verify the semantics, not the shape.** Finding the syntax a claim describes is not confirming what it evaluates to — and a grep that *matches* feels like confirmation, which is what makes this one stick. (Same batch: the two call sites really were written `configureRefractor(refractor) ?? refractor` and bare `refractor`, exactly as the ticket said — and both named one singleton, because `refractor/lib/common.js` ends `export {refractor} from './core.js'`. The grep matched and the conclusion was still false. One `===` would have settled it.) Ask what the claim **predicts that you can run**, then run that.
- **Push big or noisy reads into subagents** (out-of-context summarization, broad multi-file searches). Relay conclusions, not file dumps.
- **A subagent's report is a description, not a result** — the same rule as the board guide and the ticket, applied to the thing you *just* asked for, which is when it is hardest to remember. Reproduce a finding before repeating it, and always before it becomes a ticket, a CHANGELOG line, or a sentence to the user. Interim notes arrive worded like conclusions. (2026-07-25: an agent's mid-investigation note about a thematic-break data-loss bug was relayed to the user as live and shipping; it was structurally unreachable — Milkdown's `list_item` content is `"paragraph block*"`, so a thematic break can never be an item's first child — and the agent retracted it itself once its test passed *before* the fix. Two more agent claims that session were right, and one of those corrected the main thread.) Weight them by whether the agent **ran** something, not by how confident the prose is.
- **Brief a subagent to *measure*, and give it standing to contradict you — this is the highest-leverage line in any delegation.** A brief that hands down conclusions buys obedience, and obedience propagates your errors at full speed and with a green suite. Say what you believe, mark it as belief, and ask for the measurement. (2026-07-25: every one of the three false premises in §2 was caught this way, by an agent disagreeing with its own brief. The sharpest case — MAR-215's agent was told which two wins to expect and that it could stop once it had them; it measured them at ~2%, reported "there was nothing to stop at," and went on to the fix that halved typing cost. A compliant agent would have shipped 2% and closed a High ticket, and nothing in the diff would have looked wrong.) Corollary: when an agent's finding contradicts your brief, that is the *expected* return on the instruction, not a nuisance — verify it and update, rather than defending the brief.
- **Lanes / parallelism:** fill lanes by default (§1) — concurrent worktree-isolated agents, each shipping its own tickets, reconciled through one integration branch (§6). Shared files are a **sequencing** constraint, not a reason to collapse to one lane: tickets that touch the same file share a lane and run in order. Investigation fans out too, and freely — it owns no files. Send parallel subagents in one message so they run concurrently — **except when using `isolation: "worktree"`, where you launch them one per message.** Concurrent worktree creation races on `.git/config.lock` (`anthropics/claude-code#34645`, closed as not planned; `#55724` measured 13 parallel agents → 5 succeeded), and the loser does not fail loudly: it silently runs in the main checkout and reports success (`#80156`, open). They still run in parallel once created; only the startup is staggered. This rule is `tri-work`'s, hard-won there and adopted here. Keep it even though the `WorktreeCreate` hook now takes a real lock — the hook only applies where the plugin is installed and updated, and is unproven on the desktop surface (`#49986` reports Claude Desktop hardcoding the worktree path with no project-hook input; that issue is about path location rather than hook invocation, so treat it as suggestive). Staggering is the layer that still applies when the hook doesn't.
  - **Verify isolation the moment you dispatch — before you report it.** Requesting worktree isolation is not the same as receiving it. `git worktree list` plus `git status` on the main checkout costs one second and is the difference between coordination and fiction. (2026-07-25: three agents were launched with `isolation: "worktree"`; **one** got a worktree, two shared the main checkout, and all three were reported to the user as isolated. It surfaced by accident, half an hour later, when the main checkout turned out to be sitting on someone else's branch carrying a third agent's uncommitted files. Recovery was clean *only* because file ownership had been mapped in advance, so the collision still produced two cleanly-scoped commits.) A cheap standing guard is a loop on `git status --porcelain` in the main checkout — but key it on the tree being **dirty**, not on branch identity, or your own legitimate checkouts trip it; and know it is blind to gitignored writes (an agent rebuilding `dist/` there will not trip it). **Retire the guard when the run it guards ends** — a forgotten one fires on your own later edits and trains you to ignore it, which is worse than not having it.
  - **Measure file overlap; don't predict it.** `comm -12` over each branch's `git diff --name-only <base>` takes seconds and is never wrong. (Same session: the predicted conflict — a shared `it.fails` map — never materialized, while the *actual* conflict was `CHANGELOG.md`, which every stream touched because the handoff rules tell each of them to. Both PRs stalled on it.) The files your own process instructions make universal are exactly the ones reasoning-from-the-plan misses. **Run it twice**: once against the lane plan's *predicted* file sets, and again at each completion against what the branch actually touched — an overlap that appears only in the second run is a queued lane to rebrief (§1), and it is much cheaper to find there than in the merge.

## 3. The work loop (per ticket / milestone)

Repeat for each unit of work. Mark the task `in_progress` when you start it. **This loop is what a lane runs** — brief each lane agent with it, and run it yourself for the lane you hold. All three critiques and §3.6's disposition rule bind inside the lane, where the context is hot; §6's reconciliation critique is an addition to them, never a substitute (a finding deferred to the seam has already lost the same way one deferred to step 5 has).

1. **Reproduce** — confirm the behavior empirically. A throwaway probe test/script is fine; delete it after (never leave `_dbg`/`_probe` files behind).
2. **Implement** the smallest correct fix that matches the codebase's existing patterns (idioms, comment density, naming — not just "make it pass"). Respect the architecture constraints in `CLAUDE.md`.
   - **Before building a mechanism, grep for the one that exists.** Name the behavior you need and search for it. If you find yourself *citing* an existing function to justify your design, you have found your implementation — call it. (2026-07-15, MAR-146: the fix cited `revealPosition`'s explicit-entry-intent semantics in its own comments *while reimplementing them predictively* in ~60 lines across three new exports. `revealPosition(view, insertAt)` after the move was the whole job: −105 lines, every test and e2e check passing untouched.)
   - **Prefer observing the result to predicting it.** If a check can run *after* the operation and read the real state, it should. Predicting what a document *would* look like is strictly harder than looking at the one you just made — the predictive cut above needed the leading heading rank, a terminating-rank rule, the post-relevel fragment, and position mapping: four independent chances to be wrong, all replaced by one question asked of the real doc. Prediction also invents ordering hazards (commit-before-verify) that observation cannot have.
3. **Critique the first cut — BEFORE you harden it.** The moment it works, stop and attack the *design*, not the diff: is there less of it? does it duplicate something? is it predicting what it could observe? what would a reviewer say the shape should be? This step exists because the end-of-loop critique (step 5) is too late to change a design — by then the approach is wearing 60 lines of doc comments, a test suite, and mutation proofs, and every one of those is sunk cost arguing for it. **Churn is the tell:** if you have written a predicate, reverted it, and written another (or edited the same file's semantics twice), the design is not settled — stop adding tests and re-ask what question the code is answering. (Same session: a doc-end special case → a content-aware predicate across four files → reverted → a narrower predicate → shipped → *then* found the one-liner.) **Act on what it finds here, before you harden — step 6's disposition rule binds at this critique too, and this is the one where it's expensive to obey and therefore tempting to skip.** A design finding carried forward to step 6 has already lost: by then it costs a test suite to act on, and "noted, low severity" is what losing sounds like.
4. **Test** — reproduce-then-fix:
   - Add/pin a regression test (for a fidelity repro, promote its `it.fails` and remove the matching gate exclusion).
   - **Prove every new test can fail — revert the exact line it pins, not the whole change, and watch it go red.** A test that passes either way is worse than none: it reads as coverage forever. Watch for a test that asserts a *downstream* observable some other mechanism already guarantees — it will pass for the wrong reason. (2026-07-15: an external-sync test asserted "no bytes posted", which a serializer early-return satisfied on its own; the guard it claimed to pin could be deleted with the suite green. The honest observable was "no serialize happened at all".) If a claim's only observable is work that *doesn't* happen, count the work.
   - Re-read the numbers a passing check prints, and ask what they'd be if the thing were broken. (Same session: a max-wait check passed at `2ms` — that was the leading edge firing, not the 2000ms cap it claimed to prove.)
   - **Assert what the user would lose, not the state your fix manipulates.** Asserting the thing you just set restates the mechanism and re-passes for free; assert the independent observable downstream of it. (2026-07-15, MAR-146: the fix cleared a fold entry, so checking `folded` — or `foldedHiddenRanges`, derived from it — proved nothing. The honest observable was the decoration class that actually drives `display:none`.) The payoff is concrete: those tests then survived swapping the entire mechanism out in a later refactor, unchanged, and *that* is what made the refactor safe to ship. A test that must be rewritten whenever the implementation changes was testing the implementation.
   - `pnpm test <focused>` → then full `pnpm test`; `pnpm typecheck`; `pnpm build`.
   - For webview runtime behavior beyond jsdom, use the `/verify` skill.
5. **Critique the diff** — run `/constructive-critique` on the change. *Verify against reality*: probe edge cases the tests miss, adversarially. (For pure bug-hunting on a diff, `/code-review` instead.) A subagent reviewer that can run its own probes finds more than one reading the diff.
6. **Address every finding — explicitly, at the critique that raised it.** This rule is numbered here but binds at **all three** critiques (steps 2, 3, 5): a finding is dispositioned the moment it is raised, not collected into a pass that runs before commit. Deferral is the failure — it converts the cheap critiques into the expensive one. Each finding lands in exactly one bucket, chosen by **value, not effort** — you are an agent; tedium is not a cost, and "this would take a while" never justifies a ticket:
   - **Fixed** — the default for any finding that matters (fidelity, correctness, user-observable behavior, dead/misleading code in the diff). Fix it *now*, while the context is hot; a low-severity finding about the change you just made is the cheapest it will ever be. (2026-07-15, MAR-146: two unreachable predicate branches were acknowledged as "defensive purity, noting only" — the dead code shipped to `main` and cost a follow-up PR the next hour. Fixing it at the critique would have been minutes.)
   - **Filed** (a ticket id, not a promise) — **only** for a finding that matters *and* is genuinely outside the session: blocked on a user decision (name it in the ticket), a design fork, or an upstream dependency — or a pre-existing bug in territory this session never touched. Big-but-unblocked is *fixed*, not filed.
   - **Declined with a stated reason** — cosmetic, speculative, or subjective-taste findings; in this repo's audit history the recurring offenders are consistency refactors of working code, hardening of paths nothing can reach, and decomposition of low-coupling files. Say so in the reply and drop them; **do not file them.** A ticket is a claim on the owner's future attention, and low-value findings priced at "zero effort to file" are how the backlog drowned in July 2026 (54 open, most of them deferred critique residue). The one borderline: a finding that is real but too small for a ticket *and* not adjacent to today's diff may take a one-line slot on MAR-141's do-inline ledger (§0) instead of vanishing — but the ledger prunes itself, so a line nobody absorbs dies there, which is the correct fate. There is no "noted". A finding you neither fix nor file will ship, and the write-up will still list it as if it were handled. When you decline, say so in the reply — an unmentioned finding reads as one that didn't exist. **Never file a leftovers-bundle ticket** ("follow-ups", "residuals", "cleanups from the critique", "polish batch" — MAR-93/117/119/127/174 are the cautionary examples). If the items matter, they're *fixed* before the session closes; if they don't, they're *declined*. A grab-bag ticket is deferral wearing a label. **Don't polish-loop either:** if a critique pass over unchanged scope returns only cosmetic or subjective findings twice in a row, stop critiquing and ship — taste iteration without new evidence is tail-chasing, not rigor.
7. **Commit** at a working milestone. Convention prefix (`fix:`/`feat:`/`refactor:`/`test:`/…), *why* in the body, `Closes MAR-NN`. In a lane, commit on the lane's own branch and stop there — **no PR, no `main`, no `CHANGELOG.md`** (§1); the orchestrator reconciles and lands (§6). Outside a lane, push.
8. **Update tracking** — Linear status + task list, as you go.

**Critique cadence, in one line:** at the design (step 2), at the first working cut (step 3), and at the finished diff (step 5) — cheapest first, because each later one can only change smaller things, and each one's findings are dispositioned (§3.6) before the next line of code is written.

## 4. Decide wisely (the judgment layer)

- **Multi-dimensional lens:** weigh correctness, fidelity/safety, performance, security, maintainability, test quality & coverage, UX/UI, cohesion/consistency — apply what fits, name the trade-off.
- **Scope honestly:** if part of a ticket is clean and part is hard/risky, **ship the clean part and re-scope the rest** into the ticket (or a new one). Never force a fragile fix into fidelity-critical code for diminishing returns. Say what you're deferring and why.
- **CHANGELOG gate is observability, not effort:** user-visible behavior in (`### Fixed`/`Changed`/…); internal correctness/tooling out (it's in git). Review `docs/BENEFITS.md` and edit in place only if a capability's story changed.
- **Every user-facing claim must be one you checked** — the CHANGELOG describes the product to someone who can't read the diff, so a plausible-but-unverified sentence there is a defect, not prose. Reachability claims are the usual offender: "gesture X does this too" needs the gesture actually driven, not inferred from the code you happened to touch. (2026-07-15, MAR-146: a CHANGELOG line claimed outline reordering hit the same bug. It was true — but only via a *terminal gap* slot nobody had probed, and it was written before anyone checked; the obvious "into" path is withheld and would have made the sentence false.)
- **Verify against the code, not the CHANGELOG,** before calling anything done.
- **A recorded number is a description — re-measure before quoting it.** Baselines, snapshots, and "current" figures in committed JSON drift the moment `main` moves, and they read as measurements because they once were. (2026-07-25: `e2e/perf/bundle-baseline.json` had drifted **62,824 bytes** behind `main`, so the "95.9 KB of headroom" quoted from it — into a ticket, as a verified correction — was actually **34.5 KB**. A rebuild and one `perf:bundle` run would have caught it, and the real number changed the ticket's priority.)
- **Don't infer a file-wide convention from its first screen.** Sample the whole region, or the "fix" is the defect. (2026-07-25: the CHANGELOG's `Fixed` entries looked blank-line-separated across the first 14 lines, and normalizing on that reading would have rewritten **33** unrelated entries — released sections run consecutive, so the sample was the anomaly and there was nothing wrong. Two apologies had already been made to the user for a mess that did not exist.)

## 5. Track & discover (keep the backlog honest)

- **Disposition discovered work by value, not effort** — the §3.6 buckets apply to pre-existing bugs, footguns, and follow-ups too: solve it this session if it matters and nothing outside the session blocks it (longer sessions are the accepted price); file via `/devlog` only when it's genuinely blocked or in untouched territory *and* worth the owner's future attention; decline the rest out loud. Don't silently absorb or drop them — but don't launder them into tickets either.
- **Never file a ticket whose reproduction you haven't run yourself.** A filed repro is a claim someone will act on weeks later, when the context is gone and the ticket is all that's left — and a wrong one costs a whole session before anyone doubts it (this loop's own §2 now opens with three such tickets). Paste the observed output, not the expected. If a finding came from a subagent, reproduce it before filing; if it can't be reproduced in-session, say so **in the ticket** rather than filing the claim as fact. (2026-07-25: MAR-222 and MAR-223 were filed from agent reports and only verified afterwards — both happened to be exactly right, which is luck, not method.)
- **Watch the filing ratio.** A session that creates more tickets than it closes is running a deficit; justify each filed ticket against the blocked-only rule in the end-of-session report.
- **Groom as you go:** cross-check whether the change *incidentally fixed* another open ticket (same root cause) — verify against the working tree, pin a regression test, close it. This catches silently-shipped work.
- **Close the loop both directions:** `Closes MAR-NN` in the commit; SHA + status comment in the ticket. On a **squash** merge, the branch commits are rewritten — cite the **merge** SHA, not the branch SHAs.

## 6. Land it

- Branch first if on `main` (`lewish/<slug>`). At a solid milestone open a PR (`gh pr create`) with a summary, the tickets, and the verification done.
- **Wait for CI green** (`gh pr checks <n> --watch`), then merge matching the repo convention — **squash** (`gh pr merge <n> --squash --delete-branch`). Pull `main`.
- Move shipped tickets to `Done` with the merge SHA; re-scope partials (update title/description, leave open).

## 7. Hand off & clean up after yourself

- Run the `CLAUDE.md` **end-of-work handoff** whenever `src/`, `webview/`, `shared/`, or `package.json` changed: `pnpm test` green → CHANGELOG → review BENEFITS → `pnpm run package` → install the VSIX + remove any legacy build → tell the user to **reload** (Cmd+Shift+P → "Developer: Reload Window").
- **Leave the tree tidy:** delete merged branches (local + remote), remove stale worktrees, `git fetch --prune`. Before any destructive branch/worktree op:
  - **Classify merged vs unmerged.** `git branch --merged` misses squash-merges — verify via `gh pr list --head <branch>` (a deleted remote + a `MERGED` PR = safe).
  - **Ask before deleting anything that would lose work** (unmerged/closed-unmerged branches). Review the actual content first — is its unique artifact already on `main`? is it superseded? — don't guess.

## Cross-cutting stance

- **Act on sensible defaults; ask only on genuine judgment calls** the code/context can't resolve (deleting unmerged work, a fidelity policy decision, a user-facing trade-off). Note the default you picked when you don't ask.
- **Report faithfully at the end:** what shipped (and where — merge SHA), what's deferred and why, what's still red, tickets created/closed/re-scoped. Distinguish what's in the CHANGELOG (user-observable) from what shipped but is internal by design.
