# Birta Writer for Mac

A hotkey-summoned macOS scratchpad running Birta Writer's real editor: full rendering, slash commands, block drag, inline calc, from the first keystroke. It is a menu-bar agent that keeps the editor warm in a panel and hides it again on demand, and that can also show a Dock icon: `Prefs.showInDock` ships off, the tour's closing checklist is where a new install is told the option exists, and an install that predates the tour keeps whatever it had. The panel sits at the ordinary window level, always: a window that will not go behind anything is a window you fight, and the hotkey brings it back in one keystroke, so anything can cover it and it stays put when you click away. The product decisions live on MAR-370; this file is how to build, run and check it.

The app ships zero behavior the extension lacks. It loads the same `dist/webview.js`, with `webview/ui/hostPalette.css` in place of the palette VS Code injects and a host profile (`shared/hostProfile.ts`) that leaves out what only means something inside VS Code: the raw markdown view, the settings UI, the read-only toggle. Images are in, because the shell has its own store for them (see "Images" below); the table of contents is in, because the window has somewhere to dock it; and spelling and grammar are in, because `SpellService` answers those lints with `NSSpellChecker`, which every Mac already has. The style check was never gated on any of that and the distinction is worth keeping straight: spelling and grammar are lints the page posts OUT for a host to answer, where the style check is computed inside the page, so it runs on every surface. Which of the four a surface can run is decided in the page from the capabilities (`initialConfig`), never by a host sending its own answer. The profile also carries the layout choices that differ between the two surfaces, of which the panel's are the formatting row, the fixed toolbar, menus that open on a click, and a find bar drawn the way macOS draws one.

## Requirements

Two facts decide whether a Mac can run the app, and each is declared once, in a place something reads.

macOS 14 or later. `Resources/Info.plist`'s `LSMinimumSystemVersion` is the one macOS itself checks before launching the app, and `Package.swift`'s `platforms: [.macOS(.v14)]` is what makes the claim true rather than advertised: SwiftPM compiles every target against that floor, so reaching for an API that arrived later is a build error and not a crash on somebody's older Mac. The extension's pair is the same shape, `engines.vscode` stating the floor and `@types/vscode` pinned to it keeping the compiler honest about it, and the two app-side declarations and this sentence are held in step by `shared/__tests__/macSystemRequirements.test.ts`.

Apple Silicon, for the published app. The release job runs `swift build` with no `--arch`, so the bundle carries the build machine's own architecture and nothing else; the runner is Apple Silicon, which `.github/workflows/mac-app.yml` asserts off the built binary rather than leaving it as a claim here. Nothing chose this, and it is one flag away from being universal: `swift build --arch arm64 --arch x86_64` produces a bundle that suits both, by compiling every target twice. A checkout builds for whatever machine you are on, so an Intel Mac can build and run the app; only the download is one-sided.

Neither update path will install a build this Mac cannot launch. The in-app updater and `scripts/update.sh` both ask the downloaded bundle about its own floor and its own architecture before the running copy is quit and replaced, and refuse with what the build wants and what this Mac is. That check earns its place because the swap is designed so a failure leaves the app where it was, and macOS reports an incompatible bundle only after the working copy is already gone. `BirtaWriterCore.SystemRequirements` is the whole of the decision, and it holds no floor of its own: the bundle being installed is what answers, so a release that raises the floor is judged against its own number.

## Build and run

Building needs Swift 6, on a Mac meeting the floor above. The Command Line Tools are enough to build; `swift test` needs Xcode for XCTest, and `mac/scripts/test.sh` points at `/Applications/Xcode.app` when it is installed. No Apple developer account: the app is ad-hoc signed, which is fine on machines you own and is not fine to hand to anyone else (see "Other machines" below).

```bash
pnpm mac:build     # production esbuild, swift build, assemble mac/build/Birta Writer.app
pnpm mac:install   # the above, then install to /Applications and relaunch
pnpm mac:run       # build, then open the app out of mac/build
pnpm mac:test      # swift test over both targets: BirtaWriterCore and the app
```

`mac/build/` is a build directory: gitignored, and whatever the last checkout produced, so a branch switch quietly changes which build the hotkey summons. `/Applications` holds the one copy you actually run, and `pnpm run install:local` puts it there as part of the end-of-work handoff, so it is never a step you take by hand.

Installing leaves the tree as it found it. `mac/.build` (the SwiftPM cache) and `mac/build` (the assembled app) are together a few hundred files and a couple of hundred megabytes, and after the app is in `/Applications` neither is wanted, so `install-app.sh` removes whichever of them that run created. Whichever already existed is kept, so a session already iterating on the shell does not lose its compile cache to someone else's install. `pnpm mac:build` is outside that rule, because producing `mac/build` is the whole point of it.

One consequence to know: `mac/scripts/measure.sh` and `mac/scripts/run.sh` both read `mac/build/Birta Writer.app` and neither builds it, so after an install into a tree that had no build directory they refuse. Run `pnpm mac:build` before measuring. The alternative was leaving a runnable, branch-shaped app behind in every tree that ever installed, which is the confusion the paragraph above exists to prevent.

The two refuse on different questions, and `measure.sh` asks the harder one. `run.sh` wants an app to run, so absence is the only thing that stops it. Every arm in `measure.sh` reports on the product, so a bundle the branch switch above left behind does not fail: it answers, and the arms that go red are whichever ones cover what changed since. `mac/scripts/build-fresh.sh` is the preflight that refuses that run, checking each hop the bundle is assembled across (sources to `dist/`, `dist/` to the page inside the bundle, the Swift half to the binary) and naming the stale one. Its header carries the failure that earned it, which is a run that blamed `NSSpellChecker` for a capability an older Swift half had not declared.

Replacing a running copy is the part worth knowing about. `mac/scripts/install-app.sh` sends SIGTERM, which the app turns into its ordinary flush-then-quit, waits for it to go, swaps the bundle and relaunches. It never escalates to SIGKILL: the buffer lives in the web content process until that flush, so a kill to win a race would trade away the bytes the whole persistence design exists to keep. If the app will not quit, the install stops and says so, having replaced nothing.

## Other machines

`bash mac/scripts/update.sh` fetches the app attached to the newest GitHub Release, checks it against the checksum published beside it, and installs it the same way. The nightly `Release` workflow builds and attaches it (`mac-app` in `.github/workflows/release.yml`), so a machine that never builds anything can stay current.

Read the warning at the top of that script before running it anywhere. The app is ad-hoc signed, with no Apple Developer ID behind it and no notarization, so macOS cannot tell you who built it, and the script clears the download quarantine that would otherwise stop it opening. That is a reasonable trade on a machine whose owner also owns the source, and it is not one to ask of anybody else. Notarization is what replaces it, and it needs a paid Apple Developer account; until then the app is not distributed to other people.

## Updating itself

Three steps, and only the last one is ever in front of anybody. CHECK asks the project's own release host what the newest release is, at launch and every couple of hours after it (`UpdatePolicy.recheckInterval`). STAGE fetches that release, verifies the checksum published beside it, unpacks it and leaves it in the temporary directory with nothing replaced. ARM hands the swap to a script that runs once this process is gone, since an app cannot reliably replace the bundle it is executing out of.

With Automatically update on, check and stage both happen on their own, so by the time anything is decided the bytes are already here. Staging is held off over a connection `NWPathMonitor` calls expensive or constrained, which is cellular, a hotspot, or Low Data Mode; the check still runs and the offer is still raised, and pressing Restart downloads whatever the connection is, because that is somebody asking. `NetworkPath` holds the argument, including why its bias runs the opposite way from every other gate on this path. The swap then goes in one of two ways. Where somebody is at the window, the offer sheet asks, with buttons held dead for a moment so a keystroke in flight cannot answer it. Where nobody is, `UpdatePolicy.mayInstallUnattended` says so and the swap goes in with nobody asked. It is one predicate rather than a chain of guards, because it is the decision that quits somebody's app and it should be checkable in one place: an update staged, the setting on, this version not declined, no offer on screen, no `/ai` run going, and `isUnattended` satisfied about the person, which is no window of the app on screen, nothing unwritten, and no input on the machine for `UpdatePolicy.unattendedIdle`. That idle time is the window server's rather than the app's, because this app is hidden nearly all the time and its own idea of idleness would call almost every session unattended. An unattended swap reopens with `open -g`, so it does not take the front from whatever the person left running, and the panel carries a notice naming the version until somebody dismisses it.

Declining a version suppresses both ways in, not only the sheet, and discards what was staged. `docs/NETWORK_POSTURE.md` is where the consent argument lives, including why this does not ride `networkEnabled`.

The app appears in the menu bar as the Birta Writer mark (see "Icons" below), unless Show in menu bar is turned off. That switch and Show in Dock beside it are bound by one rule, which `BirtaWriterCore.AppPresence` holds and both rows read: either surface alone is enough to reach the app, and whichever is currently the last one on cannot be switched off, so a running copy is never left with no way in but a hotkey somebody may have forgotten. The rule is symmetric on purpose, because the forbidden state is one state reached from two directions and a guard on whichever switch was built first leaves the other free to walk into it. Clicking the item summons or hides the panel; Control-click or right-click opens its menu, which holds the panel toggle, About, Settings and Quit and nothing about files. About is in that menu as well as in the app menu because an accessory app's app menu is invisible until a Dock icon is switched on, so for most installs the menu-bar item is the only route to it. The window is the app's own rather than `orderFrontStandardAboutPanel`, and the links are what decide that: the standard panel takes them as attributed-string links inside a text view, which the keyboard cannot reach, and `LinkButton` is a real button. It draws the mark, the name, the version, then Website, Source Code and Report an Issue as buttons of one width stacked under each other, with the copyright underneath from `Info.plist`'s `NSHumanReadableCopyright`. Buttons rather than a row of link text, which is the one shape none of the About windows on this machine uses: Claude for Mac stacks Help and Get support the same way, and Finder, Linear and Figma have no links at all and end on the copyright. A build that carries no stamped version says so in words instead of showing `0.0.0`, which identifies no release and would be quoted into bug reports as though it did. `BirtaWriterCore.AboutInfo` holds that rule and the one repository string the source link, the issue link and the updater's release feed all derive from; `shared/__tests__/macAbout.test.ts` ties that string to the repository `package.json` publishes from, since Swift cannot read the manifest at runtime. Press ⌘⌥⌃J to summon or hide from anywhere; Esc twice hides it (one Esc belongs to the editor: it closes a menu or selects the block). Cmd+F opens find and Cmd+K the link prompt through the Edit menu, since those are VS Code keybindings in the extension. Settings (from the menu, the gear in the toolbar, or ⌘,) is three panes in the shape macOS settings windows have, which is what `toolbarStyle = .preference` draws: General is the app itself on this Mac, AI Agent is the command `/ai` hands a prompt to, and Advanced holds the gestures that undo rather than set. Which rows sit on which pane is `SettingsForm`'s to say, and `SettingsPaneTests` checks each pane against that declaration by reading the labels back off the live view hierarchy. Its window is titled for the app rather than for the pane, which is the one place it departs from that shape on purpose: a multi-pane settings window names the selected pane, and that assumes the app is named somewhere else on screen, which for an app with no Dock icon it is not. A Dock icon weakens that argument without reversing it, and a window titled one way with the icon on and another with it off would be worse than either. The toolbar under the title names the pane.

General holds every row the welcome screen asks, in the same order and the same words, and since that screen left the launch path it is where all of them are answered: the summon hotkey, where your notes live (iCloud Drive, and a Location row when that is off), whether the app saves as you type, which note a summon opens and what a new one is called, and how the app behaves as an application (the Dock icon, starting at login, updating itself, and link previews). The two screens are one layout on purpose: the questions screen is still built for a development build's Show Welcome and for `BIRTA_MAC_OPEN_WELCOME=1`, and a row it shows is the same row General shows, so a checking run that reads one has read the other. AI Agent holds the `/ai` switch and the command it runs, under three sentences saying what that needs and who might charge for it. Advanced holds the reset, and, in a development build only, the button that shows the welcome screen again. See "Network" below for what link previews turns on.

## Opening a file

File, Open (Cmd+O) is one way in, and the folder button the titlebar draws beside the file's name is the other. Both open the same chooser, which offers exactly the formats `DocumentTypes.accepts` will let through, so a person cannot meet a greyed-out file the app opens perfectly from the Finder. The chooser is the whole of what those two add: the rebind itself is `openDocument(at:)`'s, the same path the Finder's hand-over takes, because a file arriving from a panel and a file arriving from the Finder must not acquire different answers to what happens to the note being left.

The app offers itself in the Finder's Open With for the formats the editor opens: `.md`, `.markdown` and `.mdx`. It never takes the default away from whatever opens those files now, because every entry in `Info.plist`'s `CFBundleDocumentTypes` is ranked `Alternate` rather than `Owner`. Joining the list is the whole request; a fresh install quietly becoming what a double click opens is not. A development build registers an entry of its own, under its own name, because the plist is one file with the flavour stamped over it.

Opening a file binds the panel to it, through the highest of `ActiveBinding`'s three slots, and File, Back to My Notes is the way out. The note being left is written first, whatever the autosave setting says, for the same reason New Note writes before it switches: being pointed at another file is not a reason to lose what was typed into this one. A Finder selection of several files hands over several, and the first the editor can read is opened, because there is one buffer and one panel.

The list of formats is `shared/documentExtensions.ts`, which is where a new one is added. Three copies restate it and none can import another: the extension's `customEditors` selector in `package.json`, the imported type declarations in `Info.plist`, and `BirtaWriterCore.DocumentTypes.opened`, which is what the app checks when a file arrives, since `open -a` consults no plist. `shared/__tests__/documentTypes.test.ts` is the only thing relating the last two to the list, and Swift and a property list were outside every copy-detector in the repository before it.

What a launch opens on is one decision with three answers, and `BirtaWriterCore.FirstRun.opening` is where all three live. A real first run gets `invitation`: nothing opens, the menu bar says where the app lives and which keys to press, and pressing them is the only route to the panel, which then comes up already holding the tour. `screen` is the questions, and no ordinary launch reaches it any more; it is kept for `BIRTA_MAC_OPEN_WELCOME=1` and a development build's Show Welcome, because retiring the rows is a separate decision from retiring the launch that showed them.

Neither is offered while the panel is bound to a document, because introducing this app's own note is the wrong thing to put in front of somebody whose panel is on a file they chose. The question is asked of the binding rather than of the launch, because a binding outlives the launch that made it: a gate on the launch defers exactly once, and the next launch would offer a tour over the same document and be refused the seed. Deferring now costs only the timing, because `hasSeenWelcome` is spent when the panel comes up rather than when the launch happens, so the invitation is offered again on the first launch that is back on the app's own note.

The tour is never written into a file the app was pointed at, whatever that file holds. `FirstRunNote.shouldWrite` refuses the `document` slot outright, and that refusal is the one the others cannot make: an empty `.md` somebody made themselves reads as `empty`, which is the state the tour is FOR in this app's own note, so the emptiness rules say yes to it. That path stays reachable after the screen is deferred, because a later launch still has the document bound.

What the app WRITES is a separate list, one extension long, and `DocumentTypes` holds the two apart. Every file the app creates is a note it named itself, so a save panel offering three formats would be offering a name the note template cannot produce.

## Opening from a shell

Settings, Advanced, Open from Terminal installs `bwr`: a symlink in `~/.local/bin` pointing at `Contents/MacOS/bwr` inside the bundle. A link rather than a copy, so an app that moves or replaces itself carries its command with it, and in a directory the user owns, so nothing about the gesture needs a password. `bwr-dev` is the name a development build offers, for the reason its hotkey and its note differ: the two bundles are meant to sit in `/Applications` together, and one name would mean whichever was installed second silently took the other's. The name is editable, because the only thing about this that can collide with somebody's machine is the word, and renaming it moves the link rather than leaving a second one behind.

| Typed | What happens |
| -- | -- |
| `bwr` | Every window comes up, as the summon key does. A call from a shell is a request rather than a toggle. |
| `bwr notes.md` | The file opens where Open With would open it, which is `OpenRouting.destination`'s answer and not this command's. Relative paths resolve against the shell's directory, which the app does not share. |
| `bwr new.md` | The path is created empty and opened. |
| `bwr ~/notes/` | A directory window rooted there. |
| `bwr a.md b.md` | Both, in the order typed. |
| `cat draft.md \| bwr`, `bwr -` | The text is written to a dated file under the app's own Application Support folder and opened like any other. `./-` is read as a path rather than as standard input, and is then refused for its extension like any other. |
| `bwr --version`, `bwr --help` | The app's version, and the usage. |

Two decisions are worth knowing before changing any of it. The command is a launcher and not a second front end: everything it can be asked to do ends in `open(1)` handing a file to the app, which is the route the Finder's Open With takes, so where a file lands stays one question with one answer. And it opens exactly what `DocumentTypes.opened` opens, rather than a list of its own; the extensionless files that fill a Unix working directory are the reason, since `Makefile`, `LICENSE` and `COMMIT_EDITMSG` are the largest class of non-Markdown on the machine and nothing in the name tells them apart from a note.

A path with nothing at it is created before the app is asked for it, which is a deviation from what an editor usually does and is forced: LaunchServices refuses a path that does not exist, so the alternative to creating it is refusing it. It is created with the mode the user's `umask` gives any other file they make from a shell, because 0600 is for a note the app named itself rather than for a path somebody typed.

`--wait` is parsed, validated and then refused, because carrying it out needs a channel back from the app saying the document closed and the bytes landed, and that is not built. So `EDITOR='bwr --wait'` does not work yet, and says so rather than returning the moment the file opens.

`BirtaWriterCore.CliInvocation` is what the words mean and `CommandInstall` is how the name gets onto `PATH`. The first is pure, so the whole invocation table is decidable without a disk or a running app; the second keeps its decisions pure and its filesystem work in three small functions at its bottom. The settings row reads the link off the filesystem every time it is drawn rather than out of a preference, because the link is the fact: a command removed by hand, or one left pointing at an app that has been deleted, has to move that switch. It reports two more things the link alone cannot say, which are whether the directory is on `PATH` at all and whether something earlier there already answers to the name.

## Saving

The app edits one file. There is nothing to file away and nothing that empties the panel; the window names the file where macOS names a file, in the titlebar beside the traffic lights:

```
◉ ◉ ◉   Birta Writer.md — Edited
```

That is the platform's own treatment rather than one of ours, and the gestures come with it. A click opens the document popover, the same Name, Tags and Where form macOS opens from a document window's title: renaming there moves the file and keeps the editor on it. Cmd-click, Ctrl-click or right-click opens the path popup: the file, then every folder above it up to the volume, each revealing itself in Finder. No proxy icon, because the panel edits one plain `.md` file and never a package, so the icon would be the same generic mark on every note.

`Edited` is drawn only with autosave OFF, where it means press Cmd+S. With autosave on the flag underneath it still rises on a keystroke and falls on the write, several times a sentence, and a word that appears and vanishes on that schedule names nothing anybody can act on; macOS says the same about its own autosaving documents.

`BirtaWriterCore.WindowTitle` holds everything about that decidable without a screen: whether the suffix is drawn at all, that its separator travels with it rather than with the name, and where the popup's walk up the folders stops. `BirtaWriter.TitleBarView` draws it as a leading titlebar accessory, which is the only way to get a leading title into a panel whose titlebar band is already the page's own toolbar, and centres the label on the height AppKit gives it rather than the one it was built with. The rest is measured against a running panel, because none of it can be seen from anywhere else: `mac/scripts/measure.sh` asserts the title's vertical centre against the close button's, that the title says one thing across a typing burst, and that the popover fills every row and its rename moves the bytes.

The popover is built rather than inherited, which is worth knowing because it looks free. AppKit gives it to `NSDocument` applications, driven by autosaving in place; a window with a `representedURL` and no NSDocument behind it gets the Cmd-click path menu and nothing else. The app is one panel holding one buffer, and adopting the document architecture to reach a popover would be a rewrite of the part that works.

The app holds as many windows as you open. Cmd+N and Open each make one, rather than replacing what is on screen, and a window is the unit of everything below: one buffer, one bound file, one title, one autosave timer. Opening a file that is already open brings its window forward instead, decided by `BirtaWriterCore.FileIdentity.sameFile` rather than by comparing paths, because two paths through a symlinked folder and a case-insensitive volume are the same file spelled differently; two windows over one note would hold two uncoordinated writers, each writing the whole file, and nothing here would notice the loss. Cmd+W closes a window through the same question a quit asks of it, except for the LAST window, which hides exactly as it always did: hiding keeps the page mounted, and that is what makes the next summon instant, so tearing it down would turn every summon after a Cmd+W into a cold start. The hotkey shows and hides the whole set, which is why every window keeps the panel's overlay manners rather than only the first. `WindowSet.swift` holds the four process-wide things that used to live in the one window there was, and why each is wrong once there are two.

A window can be rooted at a folder. Open (Cmd+O), Open With, a Dock drop and `open -a` all take a folder as readily as a file, because `Info.plist` claims `public.folder` (as a Viewer, ranked Alternate, so the app joins a folder's Open With list and never becomes what double-clicking one does) and `WindowSet.openDocument` asks the disk which it was handed. A rooted window (`Coordinator.explorerRoot`) declares the `projectFiles` capability to its page and no other window does, which is what keeps the explorer off every single-file window: the page draws the tree, the host answers it. `BirtaWriterCore.DirectoryListing` is the host's half with no window: one folder per ask, folders first in the Finder's order, each entry saying whether the editor opens it and whether the Finder hides it (the page filters on the hidden-files setting, so the toggle needs no re-list), and the root questions the routing asks, with paths on the wire relative to the root and refused when they would leave it. `DirectoryWatcher` is one FSEvents stream per open root, shared by every tab of the group, reporting the folders that changed. `OpenRouting` decides where a file opened from outside lands, in order: a file already open fronts its tab; a file under an open root joins that window as a tab, which is also how a Finder open selects its row, because the tab's own load announces it; the vacant window in front takes it over; otherwise the Open files in setting (`Prefs.openFilesIn`) picks a loose tab beside the window in front or a window of its own, and for the window the show runs with the panel's tabbing mode disallowed so the system's Prefer tabs preference cannot fold it. A row of the explorer, and Go to File over a rooted window, take the other arm of the same file (`explorerDestination`): the file replaces the one in the tab that was clicked in, the way a notes sidebar navigates, unless a new tab was asked for (Cmd+click, a middle click, Cmd+Return, the row's Open in New Tab) or the tab holds text that is not on disk and autosave is off, in which case it opens beside. That arm stays in the clicked window with one exception: a file open as another tab of it fronts that tab, and a file open in some other window fronts that window instead of opening here again, whatever the click asked for, because two buffers over one path hold two writers and the later one silently takes the earlier one's edits. `Coordinator.replaceFile` is the in-place half: it flushes the page, writes the leaving file on the hiding rule, and re-checks for unsaved text before rebinding. A right-click on a row is the app's own `NSMenu`, built from `BirtaWriterCore.ExplorerMenu` and put up at the point the page reported, because every row action is the host's (a tab, the Finder, the pasteboard, the Trash). New Note and New Tab in a rooted window make the note in the root, as a tab, with no app-wide slot, because a note in somebody's project is not the app's current note. Which file a folder opens on is `DirectoryListing.firstToOpen`'s rule: the most recently used file inside it, else the newest openable file at its top level, else a note made there, since a window is always one buffer. `mac/scripts/measure.sh` opens a temp tree, reads the listing back, writes a file into it and waits for the change to reach the page, then opens a file under it from outside and reads it back as a tab.

A window holds tabs, and a tab is a window: AppKit's window tabbing groups whole panels under one bar, so every tab is a `Coordinator` with its own page, its own file and its own autosave, and every rule above about windows holds for it. What is new is the group, and `BirtaWriterCore.TabGroupPolicy` holds the decisions about it: which windows may share a bar (one identifier for loose notes, one per folder for directory windows, under the bundle id so a development build never merges with the release), what Cmd+W and Shift+Cmd+W do as the count changes, which chord picks which tab, and how the titlebar band splits once the bar has taken a row of it. That split is the part with a seam into the page. macOS draws the tab bar as a row of the titlebar band, under the title row and over the page, so the band the page sizes its first toolbar row from grows by the bar; `Coordinator` reads the bar's row off the accessory AppKit inserted, sends the page the title row as `--mac-titlebar-height` and the bar as `--mac-tabbar-height`, and the host page (`mac/Resources/index.html`) spends the second as a gap under its first row so content, the drawer panels and the find bar all clear the tabs. The page's formatting row is no part of the band: it sits below the tab bar as the top of the content area, level with a docked side panel and starting where the panel ends, and whether it is open is the app's one answer for every window and tab (`Prefs.formattingRowExpanded`, asked for by a page's gear switch as `setFormattingRowExpanded` and pushed to every page, the asker included, under the same name). The chrome that hangs off a control in the title row (a dropdown, a tooltip, the sidebar's flyout) would otherwise open into the tab bar's row and be painted under it; the host page hands the bundle that strip as `--host-strip-under-topbar`, and `hostStripUnderTopbar` in `webview/utils/headingUtils.ts` is what each of them asks before opening downward. The band's height is watched through `contentLayoutRect`, because AppKit inserts its tab bar accessory a turn after `addTabbedWindow` and no layout pass of the full-size content view notices. The drag strip (`TitlebarDrag`) is laid over the title row alone for the same reason: over the whole band it would take the clicks meant for the tabs. `+` on the bar and the system's New Tab rows arrive because `AppPanel` answers `newWindowForTab`, and every tab reads its file's name because the panel's hidden title is set to it (the Window menu lists windows by it too). Cmd+1 to Cmd+9 and Shift+Cmd+] and [ are one `NSEvent` monitor beside the double-Escape one, taking a key only from a key window with two or more tabs, so with one tab every chord reaches the page as before. `mac/scripts/measure.sh` opens a tab and reads the bar, the `+` button and the strip's height back off the live window.

The command palette (Cmd+Shift+P) and Go to File (Cmd+P) are one panel, `PaletteWindowController`, over one list, and the list is derived rather than written: `PaletteSources` reads the menu table (`AppMenu.rows`, each row performed through the selector and payload its menu item carries, gated as `AppMenu.applyState` gates it, so the palette and the menu bar cannot disagree about whether a tool exists or what it is called right now), the editor commands the page posts as `paletteCommands` where no menu row names them, the other windows, the Settings rows one group per pane (`SettingsForm`, opened through `SettingsWindowController.show(paneNamed:revealing:)`), and the files a window can reach. Ranking is `BirtaWriterCore.PaletteModel` over `FuzzyMatch`, a subsequence scorer that prefers word starts and runs and returns the letters it matched for the row to draw, both pure and tested with no window; recents are `Prefs.paletteRecents`. Files in a directory window come from `BirtaWriterCore.FileIndex`, a walk of the root built off the main thread by `WindowSet.fileIndex(for:)` and dropped when the root's watcher reports a change, so the palette opens on what is indexed and refreshes when the rest lands; a window on a loose file gets the notes folder and the recents. No dependency, on purpose: the whole of it is a few hundred lines of AppKit over the tables the app already keeps. `mac/scripts/measure.sh` opens it over the directory window, types, and reads the top rows back.

A launch puts the windows back. `WindowSet` records the open set as it changes (a window made, closed, fronted, moved or rebound), one group per tab bar with its tabs in bar order, and `openAtLaunch` rebuilds it back to front, each group at the frame it had with the tab that was showing selected, and the one you last had the keyboard in at the front; `BirtaWriterCore.OpenSet` holds the recording and the launch rules, checkable with no window server. Three of those rules are worth knowing. A file the launch was asked to open (Open With, a Dock drop, `open -a`) comes to the front of whatever else comes back, fronting its existing window rather than opening a second one. "New windows open with" set to "New file" puts a blank note in front of the restored set rather than in place of it, and fronts an empty note that is already open rather than adding another. With nothing recorded, the one window opens on the most recently used file that still exists, then on what the settings name. The three file settings (`ActiveBinding`) go on deciding which setting a rename writes back to; they no longer decide what a launch opens, and the document setting is released when the window holding it closes. A settings change that reloads every window (a publishing target) leaves each on its own file, because `Coordinator.rebindFromSettings` walks the precedence from the window's own slot rather than from the top, and a window on a file no setting names stays where it is. `mac/scripts/measure.sh` checks both: the reload leaves two windows on two files, and a quit and relaunch under one defaults domain restores the same windows with the same one in front. Per-window frames after a relaunch are on the manual checklist below.

Everything the note can DO is in the menu bar, where macOS keeps it: File has New Note, Open, Open Recent, Save, Save a Copy As, Back to My Notes, Copy Everything, Share and Reveal Last Save in Finder.

Some of those rows are also buttons in the titlebar, after the name and its chevron, drawn while the pointer is on the band: a compose mark for New Note and a folder for Open, followed by a command key for the Command Palette, which is the way to every other row. The folder raises a menu rather than the open panel: Open… first, then the recent files, then Clear Recents when there are any. They are there because these are the gestures this app's menu bar is worst at offering: it appears only once the app is frontmost, and there is a Dock icon to drop a file on only for somebody who has turned Show in Dock on. Each takes its label and its printed chord from the `AppMenu` row it repeats, so a button and a menu cannot come to disagree about what the gesture is; `TitlebarActions.swift` holds the argument for the symbols and the ones rejected. Open Recent is the row whose contents the table does not hold: `RecentsMenu` fills itself when it is opened, so the File menu's submenu and the list under the button's Open… row are one menu rather than two that agree today, and `RecentFiles` decides what the list keeps, where the More boundary falls and when a row says more than a file name. The list holds the FOLDERS opened as directory windows as well as the files, in one recency order rather than a group each, because going back to a folder is the same gesture as going back to a file; what a split would have bought is telling the two apart, and the Finder's icon on each row buys that instead. `PaletteCatalog` filters the folders back out of Go to File, which is about files. The room they take is held whether or not they are drawn, which is `TitleBarView`'s rule rather than a preference: the drag strip starts where the accessory ends, and a width that moved on hover would leave the strip lying over the buttons it had just made room for. The title pays for that in name length, at every window width.

- Automatically save changes (Settings, on by default) writes as you type, after a short pause and never later than a ceiling that continuous typing cannot outrun. That ceiling is the whole crash-safety story: it is how far the file is ever allowed to trail the editor.
- Cmd+S writes now. With autosave on it is a flush and an acknowledgement rather than news; it earns its place by being the key everyone presses, and by being the write that happens when autosave is off.
- Cmd+N starts a new note, in the folder the scratchpad lives in, named by the date. No Save sheet, and that is the macOS answer rather than a shortcut past it: the buffer is written before the switch every time, so there is never an unsaved change to ask about. A bound document is left alone, because New Note makes a note in the app's own folder rather than closing the file you pointed it at.
- Shift+Cmd+S writes a COPY somewhere you choose. The panel goes on showing the note, still bound to the same file, which is what every other editor on the machine does.

Format, View and Help are menus of the app's own, and Format is where the panel's second toolbar row goes: the marks and the inserts on the menu itself, with Paragraph Style and Lists as submenus, because each of those is one question with many answers and a flat list of every heading level is one nobody reads to the bottom of. View holds the zoom trio, the content font, the table of contents, the two check settings this shell can honour, and folding. Focus Mode is absent, withdrawn by `absentUnder` on the command rather than by leaving the row out of the table: the panel's toolbar cannot be hidden, which is the chrome the mode exists to take away, so the whole of what it did here was silence the style check. The sidebar does not put it back, being one press on the toolbar already. Help holds the cheatsheet and the three destinations the About window names, and assigning `NSApp.helpMenu` is what brings the system's own search field, which searches menu items.

The Window menu authors Minimize, Zoom and Bring All to Front, and nothing else. Fill, Center, Move & Resize and Full Screen Tile are AppKit's, inserted into whatever menu is `NSApp.windowsMenu`, with the chords this macOS gives them; authoring a copy of those here would freeze one that goes stale with no way to notice. Enter Full Screen is AppKit's too and lands in the View menu, which is where macOS puts it and where `AppMenu.Menu.takesSystemRows` reserves it a rule to sit under.

The panel is an ordinary window among other applications' windows, and `BirtaWriterCore.WindowPolicy` is where that is decided and argued: one Space rather than every Space, never drawn over another application's full screen, and able to take a full screen of its own. Which Space follows the Show in Dock setting, since that setting is already the reader saying which kind of program this is. `PanelWindowPolicyTests` reads the flags off a built window and `mac/scripts/measure.sh` off a live one, because the absences are the load-bearing part and an absence is what no reading of the source catches.

What follows from being an ordinary window is that a window brought forward from inside another application's full screen cannot come to the reader, so macOS switches to the Space the window is on instead. That switch is a window-server transition whose tail undoes the activation the show issued, and the Space arrives with the application it remembers in front. `BirtaWriterCore.SummonActivation` is the rule for issuing that activation again once the switch lands, and for telling a Space change the app caused from one the reader made themselves. It is armed from `WindowSet.windowWillShow`, which every route forward passes through, for the same reason `previousApp` is captured there: the hotkey is the usual way to meet this and it is not the only one. The gesture itself is the app's to check, the way `Coordinator.hide` says of full screen: go full screen in another application, press the hotkey, and this app is the one in front when the Space arrives.

`AppMenu` is the one table every menu is built from AND the list declared to the page as `hostShortcuts`, so the keyboard cheatsheet prints what the menu actually binds. Two lists kept by hand would eventually print a key nothing binds, and a cheatsheet that lies is worse than one that omits.

A row that runs an editor command binds the chord the extension contributes for that same command, and `shared/__tests__/menuChordParity.test.ts` reads both tables to hold them together. The app ships zero behavior the extension lacks and the keyboard is behavior, so a gesture meaning heading 1 in one surface and nothing in the other is the same defect as a button doing two things. That guard asks the half a keyboard check usually forgets as well: every contributed chord the app does NOT bind is written down with the reason it stays absent, so a new keybinding in `package.json` fails until somebody has answered whether the app wants it too. The deliberate divergences carry their reasons in the same file.

The printing rule follows from where the binding lives. A menu key equivalent is not a claim about the binding, it is the binding, so the panel's tooltips print it (`webview/commandChords.ts` resolves a command to a chord through the declaration). Inside VS Code the same commands are rebindable and the page cannot read the user's binding, so it prints nothing and the cheatsheet links to VS Code's Keyboard Shortcuts instead.

`BirtaWriterCore.AutosavePolicy` is the one rule and the only pure piece worth having, and off is a promise in both directions: the app does not write while you type, and it does not write behind your back when the panel goes away either. Hiding is putting a window away in an application that is still running, so nothing is lost and nothing is asked; quitting is the end of the buffer, so it asks, as a sheet with Save, Discard Changes and Cancel. A quit nobody initiated writes instead, because there is nobody there to answer and something is waiting on the process to go. Cmd+S is the one trigger the setting has nothing to say about. Its tests pin every arm, including the one where the setting must change nothing, and `measure.sh` checks the two the app alone can answer.

The editing controls are on a second row of the top bar, under the titlebar row, which the window's own chrome owns, and under the tab bar when the window has one. The row is a child of `.editor-topbar` rather than a strip of its own, and that is the whole design: the bar's height is measured from the element, so the content's top padding, the find bar's offset, heading scroll margins and every popup's placement follow a second row without being taught about it, and a popup can no longer paint over the row because the geometry that keeps popups out of the bar's band now describes a band with two rows in it. It carries no ground, radius or shadow of its own, and no rule between it and the row above: they are one piece of chrome, and a line drawn across the window between two rows of it reads as two bars. The hairline goes under the pair, where chrome meets text. The row spans from the window's leading edge rather than starting under the first row's inset, which exists to clear the traffic lights and belongs to the row that sits beside them, and its controls are centred in it. Centring uses `justify-content: safe center`, which is one declaration rather than a resize listener: centring a row that overflows pushes the overflow out of both ends and makes its start unreachable, and `safe` falls back to start alignment exactly when the row stops fitting, which is exactly when the chevrons appear.

Whether the row is showing is a setting rather than a button: Settings > Appearance > Formatting toolbar, and the same switch in the toolbar's gear menu, one answer for every window and tab (`Prefs.formattingRowExpanded`), off by default. A row of formatting controls is a question asked once, and a button on the bar of every window was permanent space spent on it; the controls the row holds are in the Format menu, the slash menu and the command palette whether it is showing or not. Open, the row shows every control that changes the document, in one fixed opinionated order, scrolling sideways when the window is too narrow for it. Two chevrons overlay its edges when there is somewhere to scroll, each shown only while the row can move that way, so a row that fits carries no chrome at all. They are overlaid rather than placed beside the row, because a button taking its own column would narrow the row on exactly the day it is already too narrow. They exist because the scroll is otherwise discoverable only by trying it: the scrollbar is hidden, since a permanent one across a row of chrome is louder than the controls in it, and a mouse user is left looking at a row that appears to end at the window's edge. There is nothing to add, remove or reorder, and the gear offers no Customize Toolbar or Hide Toolbar: two controls and a fixed row is not an arrangement worth offering to rearrange, and the top bar is the only route to search and settings, so it does not hide.

## Dragging the window

How tall that band is comes from an EMPTY `NSToolbar` the panel installs for the height alone (`AppPanel.installBandToolbar`). A bare titlebar is shorter than the unified toolbar every document app on the system wears, and the band has always been drawing as one: the window's furniture then reads as sitting high in a strip it shares with the page's controls. macOS centres the traffic lights on whatever height the band has, so asking for the height is what keeps their placement the system's rather than a number this app would own and have to re-apply on every layout. Nothing is ever put in that toolbar; the title is a leading accessory and the page's controls are HTML, and an item there would be the second bar `TitleBarView` exists to avoid. The number itself is written nowhere: `Coordinator` reads it off `contentLayoutRect` and hands it to the page as `--mac-titlebar-height`, and `TitlebarBandGeometryTests` asserts the band is taller than a bare titlebar and that everything in it shares the traffic lights' axis, rather than asserting a figure the system owns.

The titlebar band is the page's, which is what put the toolbar up beside the traffic lights and what made the band impossible to grab: the web view is pinned to all four edges of the content view, so every mouse event in the band reached the page. `-webkit-app-region: drag` is not an answer here. It is Chromium's, and WebKit does not implement it at all, dropping the property rather than ignoring the value, so nothing the page declares can make a region draggable.

`TitlebarDragView` is a transparent AppKit view above the web view, spanning only the stretch of the band that neither the window's chrome nor the page's controls are using (`TitlebarBand.draggableSpan`); a strip across the whole band would swallow the clicks meant for Find and the gear. It hands the drag to `NSWindow.performDrag`, so snapping, Spaces and the menu-bar edge behave as they do for every other window, and it reads `AppleActionOnDoubleClick` for the double click rather than choosing zoom or minimise itself. `mouseDownCanMoveWindow` is deliberately not the mechanism: it would hand AppKit the drag at the cost of never delivering `mouseDown`, which takes the double click with it.

The page reports how wide its trailing controls are, not where they start, because the cluster is right-aligned: the width changes only when the set of controls does, so the shell refits the strip locally on every resize instead of waiting on a round trip to the page. `mac/scripts/measure.sh` asserts the strip's live frame against the title's right edge and the page's controls, which is everything the drag depends on; the drag itself needs a real pointer and an Accessibility grant these checks do not have.

None of that is a fork of the editor. `formattingInSecondRow` and `fixedToolbarLayout` are ARRANGEMENTS in `shared/hostProfile.ts`, declared by this shell and read by `webview/`, and which controls dock is derived from `ITEM_MUTATES` rather than listed: a control docks exactly when it changes the document. The extension could declare the same two tomorrow and get the same panel.

On a first launch no window opens at all. `FirstRunPopover` hangs off the status item with one sentence and the chord, the panel stays down until the chord is pressed, and it then comes up on the tour. A fallback opens the panel anyway if the chord never arrives, and a shorter one when macOS refused the chord, since there is then no gesture to wait for. Every question the old screen asked now takes its default; `Prefs.applyOnboardingDefaults` is still where those are written, and its header carries the constraint that matters more now than it did, which is that it must never grow a write that turns the network on. Rich link previews and embeds is the row that makes that matter: it ships off, and with no screen to offer the switch nothing turns it on.

That screen is still built and still checked, under `BIRTA_MAC_OPEN_WELCOME=1` or a development build's Show Welcome: the app's own icon, then the three groups General repeats, then All Settings and Continue. It takes the panel over rather than opening a window beside it, because a launch that reaches it has nothing to edit yet; the titlebar names the application there, and names nothing that can be clicked. Every row is a live setting, written the moment it moves, which is why there is no Cancel.

The window itself is quiet until you point at it. While the pointer is elsewhere the panel is the page, the traffic lights, the window's title and the top bar's search and settings; the formatting bar along the bottom fades in when the pointer arrives and out when it leaves. The shell owns that: `AppearanceObservingView`'s tracking area is the one source of truth, and it tells the page by setting `mac-resting` on the body, which `mac/Resources/index.html` styles. That stylesheet also carves the traffic lights' corner out of the toolbar, takes its bottom hairline off, and turns off elastic overscroll, which would otherwise rubber-band the fixed toolbar away from the top edge. All three are facts about a window rather than about the editor, which is why they are the host page's and not `webview/`'s.

Layout: `Sources/BirtaWriterCore` is the host-free half (hotkey parsing, the flush/seq guard ported from `shared/saveFlushController.ts`, atomic writes, the autosave rule, the agent request codec, the bridge codec and the boot config); `Sources/BirtaWriter` is the AppKit/WebKit app. Both have a test target, and the app target is tested the way it is built: `Tests/BirtaWriterTests` constructs a real window controller, lets AppKit lay its panes out, and reads the live view hierarchy back, all before anything is shown, so it runs in CI alongside the core's tests. What still needs a running app is what needs the page, the pasteboard or a real keystroke, and that is `scripts/measure.sh`. `Resources/index.html` is the page template, served over the `birta://app/` scheme with the CSP and theme class filled in; `scripts/build-app.sh` assembles the bundle by hand, no Xcode project.

## Asking an agent

`/ai` works here, and Settings holds the command it runs, in the same shape as the extension's `birta.agent.command`: a shell command with `{prompt}` where the quoted request goes. A command tuned for the extension can be pasted in unchanged, because `BirtaWriterCore.AgentRequest` is a literal port of the extension's composition and its tests carry the same cases.

The app writes the note to disk before the run, always, whatever the autosave setting says. That is not about safety here: the agent edits the FILE, so the bytes it opens have to be the bytes on screen and the `path.md#L1` reference has to name something real.

Copy Reference for AI Agent, on the selection palette, is the other half: it puts the note's path and the lines you are on (`/Users/you/Documents/Birta Writer/Birta Writer.md#L12-L20`) on the clipboard, with the selected lines quoted in a markdown fence when there is a selection, for pasting into an agent somewhere else. `BirtaWriterCore.AgentReference` decides the shape, as a port of `src/agentBridge/format.ts` whose tests mirror that file's, and the note is written to disk first for the same reason `/ai` writes it. Its header names the two places the two surfaces deliberately differ, of which the visible one is the path: ABSOLUTE here where the extension's is relative to your workspace, because a tool working inside a project resolves a relative path and the app's note is not inside anybody's project.

One real difference from the extension, which is why it is written down rather than left to be discovered: the path above. The merge is not a difference any more. `BirtaWriterCore.AgentLandingPolicy` decides what a finished run does with the panel by the same rule the extension keeps: a panel in step with the hand-off takes the file, and a panel holding bytes the run never saw is never read over, its disk bytes going to the page to fold the agent's changes around what was typed. The merge engine itself was always in the page rather than in either host, so both surfaces have had it all along; what the app lacked was a host that asked for it.

## Images

Paste or drop an image and it is saved into an `Attachments` folder beside the document, named by a hash of its own bytes (so pasting the same screenshot twice writes one file), and referenced from the markdown as `Attachments/<name>.png`. The reference is relative on purpose: the note stays portable, and nothing in a file you might share names your home directory.

Saving a copy carries them. The images the note actually references are copied into an `Attachments` folder beside the file you chose, and the references are already correct there, which is why nothing in the document text has to be rewritten. Images the folder holds but the note does not use stay behind, because an attachments folder accumulates everything ever pasted and a note that uses one screenshot should not drag the rest of it along. If a file cannot be copied the save still happens and an alert names what stayed behind, since the text is what you asked to keep.

The page reaches those files through the same `birta://` scheme that serves the app, with the document's own folder as a second resource root (`BirtaWriterCore.ResourceRoots`). A document cannot read outside that folder: the request path is refused before it touches the disk if it traverses, and the resolved path is refused if a symlink leads out.

How much that folder holds is the user's choice, and worth knowing when making it. The default scratchpad has a folder of its own, `Birta Writer`, in iCloud Drive or under `~/Documents`, so the root starts as that one directory with an `Attachments` folder in it. That is a weaker guarantee than the old Application Support location gave, and the difference is worth stating rather than glossing: those folders are in the user's own space, so anything they put beside the note is inside the root too. Point the note's Location at a file in a large directory and every file beside it becomes readable by a document that references it, which is the same bargain VS Code's `localResourceRoots` makes for a workspace. It is not a reason to avoid the feature; it is a reason not to point the app at your home directory, and a reason the default folder is one the app names rather than `~/Documents` itself.

One thing to know before reading a failure in the paste check. `measure.sh` drives the paste by sending the editing selector to the web view, not by pressing the menu's key equivalent, because an accessory app driven from a shell frequently cannot take activation, and a menu chord with no key window reaches nothing at all. Delivered the other way it failed intermittently and looked exactly like a defect in the editor, which is worth knowing because the symptom points at the wrong layer: ask the app what it saw at the moment of the chord (`NSApp.isActive`, `panel.isKeyWindow`) before believing the editor did anything wrong. What the check therefore covers is the pasteboard, WebKit's own paste handling, the bridge and the store; what it does not cover is the menu binding, which needs a real keyboard.

## Icons

Three, all committed and all regenerated by `bash mac/scripts/make-icons.sh` from the SVGs beside them in `mac/Resources/`. The marks are drawn in a private repository, which stays the source of truth; the copies here are deliberate, so that a build never depends on that checkout and a public clone can still regenerate. Regenerating needs `rsvg-convert` and ImageMagick, the same two the extension's `media/icon.png` is drawn with. No build step needs them: because the outputs are committed, no build machine or CI runner has to have either. All three are byte-reproducible, so a diff on one of them means the artwork changed and never that it was regenerated.

`AppIcon.icns` is the app icon, named by `CFBundleIconFile` in `Info.plist`. macOS does not round an app icon for you, so `make-icons.sh` cuts the artwork to the shape: Apple's grid puts 824 square of art on a 1024 canvas at corner radius 185.4, with the margin the system's own drop shadow is drawn into.

The DEVELOPMENT flavour wears the dark mark instead, `AppIconDev.icns`, cut the same way. The reason is that the two builds sit beside each other in the Dock with their names not shown, so before a pointer rests on either one the tile is all there is to tell them apart; the `[DEV]` in the name is only reached by hovering or by the app switcher. `build-app.sh --dev` copies it in under the release icon's file name, so `CFBundleIconFile` stays one value; `shared/__tests__/appFlavor.test.ts` holds the pairing.

The mark is the two-line Birta Writer lockup, the same artwork the extension's Marketplace icon flattens, and it carries a known trade at small sizes: `Writer` is drawn large enough to survive the 32 square slot, and `Birta` above it is not, so at 32 the top line reads as texture rather than as a word. Below that, at 16, neither line survives and the icon is a coloured tile. That is a property of the artwork rather than of the export, so the place to change it is the brand repository; regenerate and look at the 32 slot before deciding a redraw fixed it, because the 1024 render always looks fine.

The notes folders carry the app's mark in the Finder, which is neither of those files: it is the app's own icon composed into the SYSTEM's folder picture at launch and written to the folder with `NSWorkspace.setIcon`. Composed rather than substituted, because handing the Finder the app icon alone gives something that no longer reads as a folder, and the tab along the top edge is the whole of what says folder rather than document; drawn into the system's picture rather than a folder shape of our own, because that picture has been redrawn more than once across releases and a copy here would be last year's folder sitting beside everybody else's. `BirtaWriterCore.FolderIcon` holds the geometry and the one decision that matters, which is that a folder already carrying an icon is left alone: the mark is a file (`Icon\r`, ending in a carriage return that is invisible everywhere it is printed) and it is the user's to delete. Both folders the app DERIVES get it, in iCloud Drive and in Documents; a folder somebody chose themselves never does, because it can be anything and putting a mark on their Documents folder is a claim rather than a decoration.

`MenuBarTemplate.pdf` is the menu-bar mark. PDF because a status item is drawn at the display's own backing scale, and a template image because macOS renders one from its alpha alone, which is what inverts it for a dark menu bar and for the highlighted state. It is drawn deliberately smaller than the bar's own thickness, which `statusItemImage` in `App.swift` sets: the SF Symbols beside it carry their padding inside the box they are asked for, so matching the size they are given draws a visibly larger neighbour.

The number is about the DRAWN HEIGHT of the mark and not about the shape of the artwork, and that distinction earns its place because the artwork has changed under it more than once. The mark today is a stroked square holding a letter, and a square reaches its own edges, so the drawn height and the box are the same thing and the number holds directly. A future mark that does not fill its box would land shorter at the same number. Check that by measuring against the running bar rather than by looking at the file: a lighter mark reads small at exactly the size that makes it the right height, and the answer to that is the drawing rather than this constant. `swift run` has no bundle to read it out of and falls back to a stock symbol.

## Themes

The app reads VS Code colour themes, and four of them ship with it: Birta Terracotta Light, Birta Terracotta Dark, Birta Terminal Green and Birta Terminal Amber. `mac/Resources/DefaultThemes/` holds the files and `BirtaWriterCore.DefaultThemes` declares the four; the build script copies the folder into `Contents/Resources`, and `DefaultThemesTests` fails when the folder and the list disagree in either direction, so neither can grow a theme the other does not have.

Provenance. They are copies of `harlan-vscode-themes` (`themes/harlan-terracotta-{light,dark}-color-theme.json` and `themes/harlan-terminal-{green,amber}-color-theme.json`), a private repository of the maintainer's own, which stays the source of truth for the artwork. The copies are deliberate for the reason the brand marks above are: packaging must not depend on another checkout being present. What the copy changes is the `name` field and nothing else, because a theme that ships with this app is named for it; a refresh starts from that repository and re-applies the rename, and the two spellings are what `DefaultThemesTests` compares. That repository carries no licence file, so the permission to bundle its work is the maintainer's own to give rather than something a file records.

The model is that a shipped theme is an ORDINARY theme. A launch copies each one into the theme library once, and after that the store cannot tell it from a theme somebody added: it is picked the same way, drawn the same way, and removed the same way. Removing one is allowed, and it stays removed, which is what `Prefs.seededDefaultThemes` is for: the folder alone cannot tell a theme nobody has been given yet from one somebody threw away, so without that record the next launch would put back what the remove button said it had taken. The record is of an OFFER rather than of the folder, it only grows, and a reset leaves it alone for the same reason a reset touches no other file on disk.

Restore Built-in Themes, the last row of Appearance's Add Theme menu, puts back the shipped themes the library is missing and does nothing else: a custom theme is untouched, a shipped theme still there is left exactly as it is, no setting moves, and nothing is picked. With nothing missing it says so rather than answering with an unchanged window. It is not offered in View > Theme, which is a picker of what is drawn now and whose one other row is a door into Settings.

The word on screen is built-in rather than default, because "default" in a settings window reads as the thing a reset goes back to.

A shipped theme's id is `default_` plus its name's slug, and the underscore is load-bearing. An imported theme is stored under `ThemeStore.slug` of its name, which emits letters, digits and dashes and nothing else, so no import can ever land on a shipped theme's file however it is named: someone who adds the original Harlan-named artwork, or a theme they have named exactly after one of ours, gets a second entry rather than a silent overwrite. Where the two names really are identical, `ThemeStore.disambiguated` adds the qualifier to the shipped one alone, so a strip of cards never offers two rows reading the same. Two IMPORTS by one name still collapse into one file, which is the store's own documented behaviour and the thing that makes re-importing a theme an update.

## Opening at login

Settings has the switch. The registration is `SMAppService.mainApp`, and there is no stored preference behind it: System Settings edits the same record, so a copy in `UserDefaults` would be a second answer that is wrong whenever the user used the other door. Settings asks the system every time the row is shown, including when the window comes forward.

`BirtaWriterCore.LoginItemState` is what the four `SMAppService.Status` values mean, and it is pure so the awkward ones can be tested. The one worth knowing: `requiresApproval` leaves the switch on and says macOS is holding it, because the registration does exist and only the launch is pending, and a switch that snapped back to off would report a refusal that did not happen. A button next to it opens the Login Items pane.

The registration names the bundle it is made from, which is the other reason `/Applications` is the copy to run: a login item pointing into `mac/build` launches whatever a later checkout left there.

## Network

Off by default, and with the switch off the app makes no outbound request of any kind. Turning it on enables three things, all of them rung 1 in [`docs/NETWORK_POSTURE.md`](../docs/NETWORK_POSTURE.md): a URL you typed goes to its own host and nowhere else.

- An embed loads in an iframe the page fetches itself.
- A link alone on its own line can render as a card of the page's own title and description.
- A pasted bare URL offers you the page's title as its link text. It is an offer: nothing reaches the file until you take it, because `pasteUnfurlAutoApply` is left at its default of false.

The shell answers the last two (`resolveLinkCard`, `unfurlUrl`) in `BirtaWriterCore.PageMetadataFetcher`, under the same rules the extension applies, and the rules are the interesting part because the input is a URL out of a document: http(s) only, an SSRF guard on the original URL and on every redirect hop, a redirect limit, a byte cap, a deadline, and HTML content types only. Every failure is the same answer, the plain link, because every failure has the same remedy.

The SSRF guard exists twice, once per surface, and the cases live in `shared/__fixtures__/urlGuardCases.json` so both test suites read them. Add a case there rather than in one suite: a rule that only one implementation enforces is then a failing test instead of a difference nobody noticed.

`resolveEmbedMeta`, the caption on a provider embed card, is answered with nothing. It needs the provider recognizer, which lives in `shared/embedProviders.ts`, and a second copy of that table in Swift is the duplication this shell has otherwise been careful to avoid. The card renders; it just has no fetched caption.

## Where the bytes are

One buffer, written to `iCloud Drive/Birta Writer/Birta Writer.md`, or to `~/Documents/Birta Writer/` with iCloud Drive off or unavailable (Settings can point the app at another file; the bytes stay with the file they were typed into) atomically (temp file, fsync, rename), on the schedule `AutosavePolicy` and the autosave setting decide. Cmd+S, New Note, saving a copy and handing the file to an agent each first ask the page to flush and wait a bounded second, as the extension's will-save participant does, then write immediately, whatever the setting says: each of those is somebody asking for it, or a path where the file is about to be read by something else. Hiding and quitting ask the page to flush too, and then do what the setting says. With the setting on, the file trails the editor by one sync-scheduler window (`webview/syncScheduler.ts`), plus the autosave hold, plus one in-flight write; the hold has a ceiling that continuous typing cannot outrun, and that ceiling is the bound. With it off, nothing is written between the moments above, and quitting asks rather than deciding for you.

## Checking it

`bash mac/scripts/measure.sh` runs the built app under `BIRTA_MAC_MEASURE=1`, drives it through that mode's debug signals, and prints the intervals MAR-374 asks about (first mount, warm summon to caret, cold recovery after the WebContent process is killed) plus idle memory, and it checks that inserted text reaches the scratchpad after a hide and survives the kill. With the autosave setting off it checks the promise the other way: the hide writes nothing, and the SIGTERM that ends the run writes rather than putting up a sheet nobody is there to answer. A figure it prints is a reading; quote it from an idle machine, never from a document.

It needs the screen unlocked and awake for the length of the run, and it refuses to start on a locked one. This is the precondition to know about, because a run takes minutes and an unattended display sleeps inside that, and because of how it fails when it does. Nothing can take activation past the login window, so `WindowSet.toggle` summons on every signal rather than dismissing, and the panel stays up and covered. WebKit then suspends idle callbacks for a window that is not on screen while timers keep running, so the page goes on taking keys and autosaving, the early arms pass, and the first arms to read anything the page schedules on idle report the product broken. The spelling and grammar arms are those. They blamed `NSSpellChecker` for a screen that had gone to sleep, which is why `hide_panel` now stops the run at the first panel that will not dismiss and says which of the two causes it was.

`bash mac/scripts/check-cli.sh` is the terminal command's own check, beside `measure.sh` rather than inside it: that one reports timings and this one asserts behaviour and fails. It walks every row of the invocation table and every refusal, and it launches nothing, because `BIRTA_MAC_CLI_DRY_RUN=1` makes the command print the request it would hand to LaunchServices while still doing its own half of the work. `BIRTA_MAC_CLI_SUPPORT=<folder>` points piped text at a throwaway Application Support for the run, as `BIRTA_MAC_THEMES_DIR` does for the theme library, and `BIRTA_MAC_CLI_BUNDLE=<app>` names the bundle the command belongs to, which is how the flavour split is checked without two real installs. So what it asserts is the filesystem the command leaves behind and the request it would make, and what it cannot reach is the app's side of the handoff: that `--summon` brings the windows up, and that an opened file lands where `OpenRouting` says. Those two are the manual checklist's.

`BIRTA_MAC_OPEN_SETTINGS=general|markdown|appearance|aiAgent|advanced` opens Settings on a pane at launch, which is how a pane is proven to construct without a person to click it. The same seam as `BIRTA_MAC_SCRATCHPAD` and `BIRTA_MAC_DEFAULTS_SUITE`, and used with them. `BIRTA_MAC_SETTINGS_SNAPSHOT=<file.png>` beside it writes a picture of that pane a moment after it opens, drawn by the views themselves; switches, popups and buttons are layer-backed and do not appear in it, so it answers how a pane is laid out and not whether a control is there.

`BIRTA_MAC_THEMES_DIR=<folder>` points the colour-theme library (`ThemeStore`) at a throwaway folder for the run, as `BIRTA_MAC_DEFAULTS_SUITE` does for the settings. A theme file copied in under `<id>.json` is listed by name, and `lightTheme=<id>` or `darkTheme=<id>` in the run's defaults puts it in that mode's slot (`Prefs.Key` in `Preferences.swift` has the whole vocabulary: `appearanceMode`, `accentColor`, `tintColor`, `sidebarTransparent`, `tocSidebarOpaque`). Under `BIRTA_MAC_MEASURE=1` a `{"type":"__birtaPageSnapshot","name":"page.png"}` message (SIGURG, the file beside the scratchpad) writes WebKit's own picture of the page with the theme in force in the trace, which the AppKit snapshot cannot see into, and `{"type":"__birtaEval","js":"<expression>"}` runs one expression in the page and traces its value, for a geometry or a class list no other probe names. Both need the page WebKit is drawing: a window occluded by another application's reports itself hidden, runs no animation frame, and answers with whatever it last laid out, so a probe that reads a layout brings the app forward first (the palette probe does).

`BIRTA_MAC_OPEN_WELCOME=1` opens the questions screen at launch, for the same reason and with the same caveat. It is now the only way to reach that screen outside a development build's Show Welcome, since no ordinary launch opens it: `FirstRun.opening` answers `screen` for `forced` alone. The same environment gate is why a scripted run cannot reach the INVITATION at all. `isUserStore` refuses it under `BIRTA_MAC_DEFAULTS_SUITE`, deliberately, so a measurement run does not put a popover in the menu bar of whoever is driving the machine, which leaves the invitation something to check by launching a real install rather than by script.

Manual checklist, because a window server and a global hotkey are outside what CI can drive: summon from a fullscreen app; type, hide, `cat` the scratchpad; quit mid-typing and relaunch; open three windows, drag each somewhere of its own, work in the middle one last, quit and relaunch, and check that all three come back where they were with the middle one in front; press ⌘T twice, then ⌃Tab, ⇧⌘[ and ⌘1, drag a tab out into a window of its own and Merge All Windows from the Window menu, and check that the Window menu carries the system's Show Next Tab and Move Tab to New Window rows; set System Settings > Desktop & Dock > Prefer tabs when opening documents to Always and check that ⌘N opens a tab; ⌘O a folder and check the explorer beside the editor, that Open With on a note inside that folder from the Finder lands as a tab of that window with its row selected, that ⇧⌘E hides and shows the explorer and ⇧⌘. shows dotfiles, and that both rows are greyed in a window on a loose file; click a second file in the explorer and check the tab moves to it rather than a tab appearing, ⌘-click a third and check a tab appears, right-click a row and check the menu offers Open in New Tab and Reveal in Finder; open one of the folder's files from the Finder while that folder window is open and check it lands there as a tab, then open a file from elsewhere and check it lands as a tab beside the window in front, switch Settings, General, Open files in to New window and check the next one opens as a window with Prefer tabs set to Always; with two tabs, turn on Formatting toolbar from the gear menu and check the row sits below the tab bar, then open the gear menu and hover Proofreading and check both open below the tab bar; press ⇧⌘P, type `sca` and check that Save a Copy As leads with ⇧⌘S beside it, press Backspace to empty the field and pick Settings, General with the arrows and Return, then Show in Dock, and check that Settings opens on that row; press ⌘P in a folder window, type part of a nested file's folder name and check the file is listed with its folder and opens as a tab; toggle System Settings > Appearance and watch the panel follow; type and watch the file change with saving on, then turn it off and confirm that Cmd+S writes, that hiding does not, and that quitting asks; open a menu, press Esc once (menu closes) and twice (panel hides); with a Dock icon switched on, open the Window menu and check that the system's Fill, Center and Move & Resize rows sit between Zoom and Bring All to Front, and press ⌘B mid-sentence to confirm that the menu's key equivalent bolds the way the editor's own keymap does, since AppKit now takes that chord before the page sees it.

Multi-window adds cases a script cannot reach, and they are the ones worth walking: open two notes and drag each somewhere, quit, relaunch, and confirm the first window is where you left it while the second cascades rather than landing on top of it; summon with several open and check they all arrive, on whatever Space you are on; put one window in full screen and confirm the others still summon over it; close down to the last window and confirm it hides rather than closing, and that the summon after it is still immediate rather than a cold mount; with autosave off, edit two notes and quit, answering Don't Save to the first and Cancel to the second, then confirm the app is still running, the summon key still works, and neither file was written.

`measure.sh` covers the claim underneath all of that, which is that the buffers are independent: it opens a second window, types into it, and reads both files off the disk. It also prints memory with two windows open beside the one-window idle figure, since a window is a WKWebView and that cost is the real price of this feature.

The editor itself stays covered by the repo's harness: `node e2e/run.mjs macHost` mounts the bundle with the mac profile in Chromium, and `BIRTA_E2E_BROWSER=webkit` runs the same suite in the engine the panel renders in. That WebKit run speaks for rendering and DOM; for typed sequences it does not (Playwright's WebKit key injection puts text after a Return on the previous line, the app's own NSEvent path does not), which is why `measure.sh` types through the panel itself.
